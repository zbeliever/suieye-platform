### 1.3 三个致命缺陷（"只是做样子"的根源）

| # | 缺陷 | 证据 |
|---|---|---|
| **A** | **确认 = 一个布尔值，没有内容** | 后端 `acknowledged_by = "operator"` 是**硬编码**；不能填处理意见、不能填措施、不能标误报、没有处理时间考核 |
| **B** | **证据黑匣子 100% 存着，前端 0 展示** | 446 条告警全部带 `image` / `overlay` / `prediction` 快照，`Alarms.vue` 里**一个字都没露出**——这是最大的浪费 |
| **C** | **同源告警不聚合** | 52 组共 149 条是同一帧（同 `record_id`）触发的多条规则，占总数 **33%**。典型：id 102/103 是同一张图触发的 `pb_too_low` + `pb_critical`，列表里显示成两条独立告警 |

### 1.4 一个重要的"反转"结论（避免做错需求）

**本系统没有报警泛滥（alarm flood）问题，不需要做降噪。**

- 实测报警率 **5.2 条/天**，EEMUA 191 可接受上限是 150 条/天
- 10 分钟窗口峰值 = **1 条**（判定泛滥的阈值是 >10 条）
- 最集中的一天 23 条，峰值告警「皮带异物」单日最多 9 条

所以：**优先级不是"降噪"，而是"能处置 + 看得见证据 + 误报沉淀"。**
同源聚合要做（33% 冗余是真问题），但风暴抑制/抑制矩阵这类重机制**本期不做**——没需求，做了就是堆复杂度。

### 1.5 现有 KPI 基线（改造后用来对比）

| 指标 | 当前值 | 行业参考 |
|---|---|---|
| MTTA（平均确认时长） | **174 分钟**（最长 613 分钟） | 关键告警建议 < 5 分钟 |
| 确认率 | 17% | — |
| 同源冗余率 | 33%（149/446） | 0 |
| 级别分布 | warning 87% / danger 13% | ISA-18.2 建议 低 80 / 中 15 / 高 5 |
| Top1 规则占比 | 皮带异物 58% | 标准建议 Top10 合计 < 5% |

## 二、行业对标（调研结论）

- **ISA-18.2 / IEC 62682**：定义报警全生命周期；报警合理化要求逐条记录「原因/后果/所需动作/优先级/响应时间」；抑制分三类（操作员搁置 Shelving / 设计抑制 / 检修停用）
- **EEMUA 191**：给出量化基准（每操作员 ≤150 条/天、10 分钟 >10 条即泛滥、抖动报警 0 条、陈旧告警 <5 条/天）
- **开源可比对象**：ThingsBoard（`ACTIVE/CLEARED × ACK/UNACK` 状态机最接近本项目）、Prometheus Alertmanager（**Grouping 分组 / Inhibition 抑制 / Silence 静默** 三机制是降噪经典）、Zabbix（事件确认+依赖抑制）、OpenNMS（拓扑相关性告警）、Grafana Alerting（静默时段）
- **开源集体空白**（= 本项目的差异化空间）：
  1. 告警不与**多模态富证据**绑定（图像 + 特征快照）
  2. 没有**工艺因果链**上的抑制（磨矿→pH→药剂→品位）
  3. 误报标注**不会反哺**规则调优 / 模型再训练
  4. 规则**不能回测**（Shadow Mode）
- 选矿特殊性：视觉信号是"早于 XRF 的早期预警"（pH 偏移 0.3 → 泡沫 5~10 分钟内变色，而在线 XRF 滞后 2~5 分钟）；告警应按**控制层级**（泡沫秒级 / pH 药剂分钟级 / 粒度小时级 / 配矿班次级）分层响应

## 三、创新点设计（按优先级）

### P0 — 让它"能用"（三件事，做完告警中心才算真系统）

**1. 证据抽屉（Evidence Drawer）** ← 投入产出比最高
点开任一告警 → 右侧抽屉：
- 左：抓拍原图 / 检测叠加图（可切换，直接复用 `/api/image/{path}`）
- 右：该场景指标快照
  - flotation：Pb/Zn 品位 + **22 维泡沫特征 z-score 雷达图**（对比正常基线）
  - safety：风险等级 / 风险评分 / 置信度 / 相机位 + 检测框标注
- 底：规则命中详情（字段 · 实测值 · 比较符 · 阈值）+ 「查看完整分析记录」跳转
- **成本说明**：数据 100% 已存在，只需要把证据按场景分型渲染出来。flotation 里 22 维特征目前只有 6 条完整，需要按分布补齐（脚本补，不改采集链路）

**2. 处置闭环状态机**
`待处理 → 已确认 → 处理中 → 已闭环`，分支状态 `误报`。
每次流转**强制填处理意见**（必填）+ 处置措施（选填）+ 处理人，写 `alarm_actions` 流水表可审计。
取代现在的布尔标记与硬编码 `"operator"`。

**3. 同源聚合（帧级分组）**
以 `record_id`（同一帧图像）为分组键，一组 = 一条事件卡，卡上显示「该帧触发 3 条规则」，展开看明细。
效果：**446 条 → 349 条**，消除 33% 冗余；同帧的 `pb_too_low` + `pb_critical` 合并成一条「铅品位严重偏低」事件。

### P1 — 让它"聪明"

**4. 告警健康度看板**：按 ISA-18.2 / EEMUA 191 口径呈现 —— 报警率、级别分布合理性、MTTA、Top 坏演员、同源冗余率、陈旧告警、误报率。**用 1.5 节的基线做成"改造前后对比"**，这是汇报时最有说服力的一页。

**5. 根因联动归因**（全站独有）
品位告警触发时，自动关联同期（±2h）的配药记录（`dosing_records`）、水质读数（`WaterReading`）、磨矿粒度 → 输出「最可能原因」排序。
依据选矿诊断树惯例：**先查磨矿再看药剂**（磨矿 −200 目变化 ±5% 可致回收率偏 3~5%，症状与药剂不足相同）。开源界无对手，且解题所需数据本项目全部已有。

**6. 静默 / 搁置（Shelving）**：限时（30min / 2h / 8h）+ 必填原因 + 到期自动恢复 + 可审计。作用到 WS 通知层（静默期内不弹窗）。演示场景：皮带异物这类已知扰动。

### P2 — 让它"自进化"

**7. 规则在线管理 + Shadow Mode 试算**：把 `flotation.yaml` 里写死的规则搬到页面可编辑（阈值/级别/冷却/启停），改之前**用历史数据回测**，给出「阈值 4.0 → 3.8 将少触发 27 条、漏报风险 X」。取代"不敢改 YAML"。

**8. 误报反哺闭环**：误报标注沉淀 → 规则调优建议（哪些规则常被标误报 → 建议调阈值或下线）+ 汇入模型再训练候选集（选矿软测量标准做法）。

**9. 工艺因果抑制（Inhibition）**：借 Alertmanager 语义，上游根因告警在场时抑制下游衍生告警。**本期不做**（无 flood 需求，且依赖因果链建模）。

### ★ 排查中发现的数据问题（需老板决策）

**1. `z_scores` 字段名骗人（根因已修）**

`predictor._predict_xgb` 传给 `zscore_features` 的归一化参数键名被写死成字面量 `"k"`
（`{"k": {"mean": 0, "std": 1} for k in FEATURE_KEYS}`），永远匹配不到真实特征名，
于是每个特征都回落到 `mean=0 / std=1`，**z 退化成原始特征值**——
`evidence.prediction.z_scores` 里存的是 `r_mean=81.7`、`n_foams=81` 这种原始量纲，
而字段注释写的是"偏离训练集均值的标准差倍数"。

- 已修：基线改为从历史真实特征分布计算；`_predict_xgb` 与 predict filter 同步修正
- **影响面：只影响展示，不影响品位预测值**（XGB 用原始特征预测，z 只是附带返回）
- 历史数据：446 条老告警里仍是原始值，接口层自动判别并用基线现场换算（`source: baseline_recomputed`）

**2. 3006 / 3033 条浮选分析记录的 features 是分割失败的产物**

| 组 | 条数 | bubble_avg_size | n_foams | texture_energy |
|---|---|---|---|---|
| 异常（整图被当成一个气泡） | **3006** | ~2832 px | ~3 | ~99815 |
| 正常（真实泡沫分割） | **27** | ~80 px | ~51 | ~0.43 |

- 后果：**特征基线样本量只剩 27 条**（告警的 22 维特征与正常组同口径）
- 现状处理：基线只用干净样本，σ 做下限保护（P5~P95 跨度 / 6），接口明确返回 `baseline_n` 与 `excluded_bad`
- **待决策**：是否重跑这 3006 张图的分割补回特征？（耗时较长）不修也能用，但基线统计强度弱

**3. 一个诚实的结论**

抽样核查发现，部分"品位偏低"告警的泡沫特征其实**全部在正常范围内**
（如 #103：Pb 1.83% 严重偏低，但 22 维特征 |z| 最大仅 1.86）。
→ 因此证据抽屉**不做因果断言**，只如实呈现"实测 vs 历史基线"，把判断交给工艺人员。

## P1 实施记录 · 根因联动归因（2026-10-13）

### 做了什么

把一条浮选品位告警放回 **磨矿 → 浮选 → 回水** 工艺链上，回溯告警发生**之前**同期三个工段的真实记录，用选矿工艺先验给候选原因排序。

**新增文件**

| 文件 | 作用 |
|---|---|
| `backend/algorithms/root_cause.py` | 归因引擎（三源检索 + 工艺先验打分 + 时间衰减） |
| `GET /api/alarms/{id}/root-cause` | 接口（挂在 `routers/alarms.py`） |
| `Alarms.vue` 证据面板新增「根因联动分析」区块 | 溯源链路 + 候选排序 + 展开机理/措施 |
| `outputs/_qa/cdp_alarms_rc.py` | 专用 QA（筛浮选 → 测量 → 展开 → 截图） |

### 三个可用信号源（全部实测确认）

| 源 | 取数位置 | 用途 |
|---|---|---|
| **磨矿粒度** | `analysis_records(scene='grinding').prediction.p80` + `condition` | 过磨 → 矿泥夹带；欠磨 → 单体解离不足 |
| **配药方案** | `dosing_records`：`froth_state` / `current_ph` vs `target_ph` / `reagents[].recommended_dosage` vs `base_dosage` | pH 抑制失效、捕收剂不足、石灰吃紧、泡沫脆化、矿浆浓度偏离 |
| **回水水质** | `water_readings`（5 点位 × 9 参数）对全历史 μ/σ 求 z | 残留药剂偏高干扰选择性、SS/COD 负荷高 |

★ 之前以为"磨矿没有 P80 数据"是错的 —— `/api/scenes/grinding` 的摘要接口没有，但 `analysis_records` 里**存着**完整粒度特征与 P80 预测（27 条）。

### 数据可达性实测（浮选告警 71 条，决定窗口设计）

| 源 | 中位间隔 | ≤60min | ≤72h |
|---|---|---|---|
| 回水水质 | **29 min** | 37/71 | 39/71 |
| 磨矿粒度 | 22.8 h | 9/71 | 64/71 |
| 配药方案 | 16.1 h | 11/71 | 40/71 |

→ 因此采用**分层窗口**：窗口内（磨矿 6h / 配药 3h / 水质 2h）视为同期证据；窗口外 7 天内作弱证据并按时间衰减降权。

### 三条不可违背的原则（写进了模块 docstring）

1. **只用告警之前的信号** —— 不允许"用未来数据解释过去"（`_decay` 对负滞后直接返回 0）
2. **不硬凑** —— 信号缺失写进 `missing`；所有候选都弱时明确说"未发现显著异常"
3. **每个结论都可回查** —— 证据带原始值、参照基线、时间距离、来源表

★ 归因不出来的情况**区分了三种**，不混为一谈：
`no_data`（该时段数据未接入）/ `too_far`（有记录但超窗）/ `no_anomaly`（数据正常，无异常可归因）

### 打分公式

```
confidence = 工艺先验(0~1) × 偏离强度(0~1) × 时间衰减 exp(-Δt/τ)
```

工艺先验表（`PRIOR`）与衰减常数（`TAU_MIN`）都写在模块常量里，可调。同类候选（如多点位水质异常）自动合并为一条、证据并列。

### 坦白的边界（演示时可能被问）

## P1 实施记录 · 直播墙「需关注」卡口径统一（2026-10-13）

### 起因

老板指出直播墙右上角「需关注」区域需要修改。**诊断后发现不是样式问题，是数据口径问题**：

| 现象 | 真因 |
|---|---|
| KPI 格写「367 条」，副行写「严重 58 · 预警 388」 | 58+388=**446**（全量告警），367 是**待处理**。同格两个口径，自相矛盾 |
| 「367」出现 2 次 | KPI 格 + 卡头红色角标 |
| 「严重 58 · 预警 388」出现 2 次 | KPI 副行 + 严重度分布条图例，一字不差 |
| 卡脚「共 446 条」 | 告警中心页写的是「349 个事件」，**跨页数字对不上** |
| 列表 `flotation · 09:06` | 场景名是英文；且 `evidence` 里的 `camera_id` / `pb_grade_xrf` / `p80` 一个都没用上 |

**根因**：告警中心 P0 引入处置状态机后，直播墙这张卡仍在读**改造前的旧字段** `unacknowledged`，从没跟着更新。

### 改动

**后端**（`backend/api/routers/alarms.py`）

1. `_build_stats` 新增 `todo_danger` / `todo_warning` —— **待处理口径**的级别构成（两者之和 == `new`），与全量的 `danger`/`warning` 严格区分
2. `_alarm_dict` 每条新增 `brief = {scene_label, metric, location}` —— 从 `evidence` 现取（浮选取 `pb_grade_xrf`、磨矿取 `p80`、安全取 `risk_score`+`camera_id`），取不到留 `null`，**不编造**
3. `GET /api/alarms` 新增 `collapse=1`：按 `group_key` 做**帧级折叠**，同一帧只保留级别最高的代表（同级保留最新）。实测 12 条 → 5 个事件，每帧一条、无重复。这与告警中心「446 条 → 349 事件」同口径

**前端**（`LiveWall.vue`）

4. 四类信息**各讲一件事，零重复**：

   | 位置 | 内容 | 数据源 |
   |---|---|---|
   | KPI 数字 | 待处理 **367** | `stats.new` |
   | KPI 副行 | 已确认 77 · 已闭环 1 | `acknowledged` / `closed` |
   | 卡头角标 | 446 条 → 349 事件 | `total` / `events` |
   | 分布条图例 | 严重 48 · 预警 319 | `todo_danger` / `todo_warning` |
   | 卡脚 | 更新于 HH:MM · 查看全部 | 本地时钟 |

5. 列表条目 meta 改中文 + 真实读数：`浮选 · Pb 1.83% · 09:06`
6. ★ 列表按**「场景 + 规则」折叠**：库里 48 条 `pb_critical` 会把 4 个展示位全部占满，呈现出来就是 3 条一模一样的告警。去重后 4 格分别是 —— 铅品位严重偏低（浮选）/ 人员闯入危险区（安全）/ 严重过磨（磨矿）/ 皮带上有异物（安全），**4 个不同工段、4 个不同问题**
7. 排序补二级键：严重优先 → 同级按时间降序（原来只有一级排序，结果不稳定）

- 1920×1080（CDP 实测视口 1904×985）：`scrollH 985` 无整页溢出，`alarmList over = 0`，4 条全部可见

## 修复记录 · 直播墙「需关注」大屏留白（2026-10-13）

### 症状

1080 及以下完全正常，**2560×1440 这类大屏上，卡片中间空掉一大片**（老板截图指出）。

### 根因

`.alarm-panel { flex: 1 }` 要填满右列，`.alarm-list { flex: 1 }` 要填满卡片，但列表**固定只渲染 4 条**。
屏幕一高，卡片被拉到 619px，列表区 496px，4 条只占 136px → **留白 360px**。

（不是样式问题，是"固定条数"与"弹性容器"的矛盾。左列的趋势图同样被拉伸却没问题，
因为图表天然会跟着容器长大；列表不会。）

### 改法：按可用高度自适应「条数 + 行式」

`fitAlarmRows()` 实测列表容器高度（容器是 flex:1，高度不随条数变化 → 测量无回环），
按三档优先级决定形态：

| 形态 | 条件 | 说明 |
|---|---|---|
| ① 紧凑单行 30px | 能放下的条数 ≤ 可用规则数 | 用不同规则直接铺满，零重复 |
| ② 两行式 48px | 紧凑会重复刷同一规则、且空间够 | 上行消息、下行「场景·读数·时间」，把高度用来承载信息 |
| ③ 密排 30px（允许重复） | 空间大到两行式也不够铺 | 宁可重复也不留白 |

配套：`.alarm-item { flex: 1 1 auto; min-height: 30px; max-height: 64px }` —— 行自己长大填补余量。
上限 `alarmRows ≤ 去重规则数`：库里「皮带异物」单条规则占 58%，纯按时间排必然连着重复，
所以**条数上限 = 去重后的「场景 × 规则」组合数**。

### 顺带修掉的诚实性问题

列表只显示 `09:06` 这种时分，但实际数据跨度到一周（10-04 ~ 10-11）→ 会被误读成"刚刚发生的"。
`metaText()` 改为**非当日显示月日**：`浮选 · Pb 1.83% · 10-11 09:06`。

### 验证（CDP 单实例内切视口，`outputs/_qa/cdp_lw_sizes.py`）

| 视口 | 列表区 | 条数 | 行高 | 留白 | 形态 |

| 1904×985 | 136 | 4 | 30 | **0** | 紧凑（与既有版式一致） |
| 1424×805 | 136 | 4 | 30 | **0** | 紧凑（矮屏降级，整页滚动） |
| 1904×1105 | 256 | 7 | 32 | **0** | 紧凑 |

### 坑

矮屏降级（`max-height: 940px`）下列表是 `overflow-y: visible`（高度 = 内容高度），
自适应会形成回环（条数 → 高度 → 条数），首测到"暂无告警"空态后锁死在最小值。
`fitAlarmRows()` 里用 `getComputedStyle(el).overflowY === 'visible'` 判定并改用固定条数。
