## 一、为什么做这个

### 1.1 工艺定位：尾矿处理是浮选的"下游出口"

平台现有的工艺链是 `磨矿 → 浮选 → 安全巡检 → 脱水工段`。**尾矿处理是浮选尾矿离开主流程后的第一站**，铅锌矿的真实路径（金徽矿业实证）是：

```
浮选尾矿浆（低浓度 15~25% 固体）
   │
   ├─▶ 尾矿浓密机（加絮凝剂 PAM）─┬─▶ 底流（高浓度 60~75%）
   │                              │      ├─▶ 尾矿库堆存（隔膜泵加压扬送）
   │                              │      └─▶ 充填站（全尾砂胶结充填，回填采空区）
   │                              │
   │                              └─▶ 溢流 ─▶ 回水池 ─▶ 回用于浮选补加水
   │                                                    └─▶ ★ 已由 water 模块覆盖（W3→W5）
   └─▶ （可选）尾矿再选回收 Pb/Zn/S/重晶石
```

**与水模块的边界必须划清**（否则就是重复建设）：

| | 管什么 | 视角 |
|---|---|---|
| **water 模块（已有）** | 浓密机**溢流出来的水**去哪、能不能回用 | 水质出口 |
| **tailings 模块（本方案）** | 浓密机**这台设备本身** + **底流固体**去哪 | 设备内部运行 + 固体去向 |

两者在"溢流"这一点上交接，**不重叠**。

### 1.2 痛点（文献实证，可被追问）

**痛点一：关键参数不稳定**
> "尾砂的给料浓度、给/出料量、组成成分和粒度分布等均能够显著影响尾砂的浓密效果……导致浓密机的**底流浓度、沉降速度和固体通量等关键参数发生波动**，浓密效果不稳定，并进一步影响后续工艺。"
> —— 《金属矿尾砂浓密技术研究现状与展望》，工程科学学报（北科大）

**痛点二：只能事后调控，构不成预警**（★ 核心痛点）
> "由于给料尾砂和浓密尾砂的**关键参数之间的数学关系仍不明确**，现阶段只能够实现在**监测到底流浓度、沉降速度异常之后**进行调控，**反馈时间长，无法构建预警系统**。"
> —— 同上

**痛点三：仍是人工手动控制，大滞后非线性**
> "某选矿厂浓密机控制主要采用人工手动控制，且浓密机生产过程的参数未知，流程上游波动大，**浓密机底流浓度和絮凝剂添加控制不稳定**……具有**大滞后、非线性**的特点，常规的控制方法难以达到良好的控制效果。"
> —— 《尾矿浓密优化控制技术研究及应用》，矿冶科技集团（BGRIMM），中国矿业 2023

**痛点四：商业方案验证的商业损失**（IntelliSense.io 智利铜金矿案例）
> 原专家系统"无法根据进料类型连续调整 setpoint"，导致"底流固体含量低、**水回收率低、絮凝剂消耗高**"，"只能在事件发生后行动"。该项目首年直接节省约 **$400k**，回收期 < 12 个月。

**结论**：这条线上的价值不是"看着仪表盘"（那已经是成熟市场），而是 **把"事后补救"变成"事前预测-推荐"**，以及 **把损失量化成钱**。

### 2.3 学术/商业前沿（我们的技术对标基准）

| 来源 | 做法 | 关键数字 | 对我们的启发 |
|---|---|---|---|
| **2026 IEEE / MetaResource**（蒙古锌矿，SG=3.459）| 多变量 LSTM 预测深锥浓密机底流浓度，滑窗 + **递归 3 小时前瞻**；提出 **"预测–评估–调节"(predicting–evaluating–regulating) 前馈控制框架** | R²=0.92 / MAE=0.42% / RMSE=0.48%；泥床稳定 5.5m，底流浓度锁定 **70~82%** | ★ **核心对标**。"单纯最大化排放速率是次优的"这个反直觉结论很有演示价值 |
| **IntelliSense.io**（智利铜金矿，商业）| 实时浓密机回路建模 + **连续 setpoint 推荐** + **虚拟传感器替代缺失仪表** | 首年省 $400k，回收期 <12 月 | ★ 我们的"虚拟传感器/软测量"叙事有商业案例背书 |
| **EDEM + FLUENT + GA-BP 神经网络**（铁矿尾矿）| CFD-DEM 耦合仿真 + 遗传算法优化 BP 神经网络找最优工况 | 出口浓度实测 60.7%（误差 2.08%）| 说明纯数据驱动可行，**不需要自己做 CFD** |
| **BGRIMM 工程实践** | 沉降原理 → **浓度软测量模型** → 专家系统优化设定 → 絮凝剂自动添加 | — | 国内工程界已认可的**落地路径**，正是我们的方案骨架 |

### 2.4 ★ 结论

**开源世界里这条线几乎是空白，但学术与商业前沿已经验证了方向（软测量 → 前瞻预测 → setpoint 推荐）。**
这意味着：**我们做出来就是"有文献背书的原创实现"，而不是"抄一个开源项目"**。同时也意味着**没有现成代码可抄，得自己写**。

## 三、需求分析

### 3.1 监测对象（1 台核心设备 + 2 个去向）

| 对象 | 监测量 | 性质 |
|---|---|---|
| **尾矿浓密机**（核心） | 给料流量/浓度/粒度（可测）、**底流浓度（难测→软测量目标）**、泥床高度、耙架扭矩/电流、絮凝剂流量、溢流浊度 | 连续过程 |
| **底流去向** | 底流流量/浓度 → 判断去向：充填（需 >75%）/ 干排 / 入库 | 决策 |
| **尾矿输送** | 泵出口压力、流量、管道（堵管风险） | 连续过程 |

### 3.2 关键指标与阈值

| 指标 | 单位 | 正常 | 预警 | 危险 | 依据 |
|---|---|---|---|---|---|
| 底流浓度 | % (wt) | 65 ~ 75 | 60 ~ 65 或 >78 | <60 或 >80 | 文献膏体充填要求 74~76% 固体；过高则堵管 |
| 泥床高度 | m | 4 ~ 6 | 6 ~ 7.5 | >7.5 | 对标文献稳定值 5.5m；过高压耙 |
| 耙架扭矩 | % 额定 | <60 | 60 ~ 80 | >80 | 压耙保护（IntelliSense 案例约束项） |
| 溢流浊度 | NTU | <50 | 50 ~ 100 | >100 | **与 water 模块 W3 同源，必须一致** |
| 絮凝剂单耗 | g/t 干尾 | 30 ~ 60 | 60 ~ 90 | >90 | 行业常见区间（实施前核对本厂设计值） |

> ⚠️ 所有阈值标注为"待与现场设计值核对"，不假装是实测标定。

### 3.3 用户视角需求

1. 底流浓度**没有在线仪表**（或仪表贵/不可靠）→ 能不能算出来？（软测量）
2. 底流浓度**快超标前**要提前知道，而不是等化验 → 提前量要够一个班次调度
3. 絮凝剂现在是"宁多不少"，能不能加得刚刚好？（省钱）
4. 泥床涨了、扭矩上来了，要提前喊"压耙风险"
5. 底流够不够浓、能不能送去充填，要有**量化判断**
6. （待定）尾矿库安全状况要不要一起管

## 五、创新点（相对开源与商业方案）

1. **底流浓度软测量 + 虚拟传感器**：把"装不起/测不准的仪表"用可测变量算出来 —— 有 IntelliSense 商业案例背书
2. **"预测–评估–调节"前馈推荐**：业内痛点明确写着"只能事后调控、无法预警"，我们把它做成**提前 N 小时给 setpoint**，正面对标 2026 年最新论文框架
3. **★ 跨模块因果链（平台独有）**：所有开源/商业方案都是**单点设备优化**；我们把 `尾矿浓密 → 回水水质 → 浮选品位` 串成一条链，直接复用平台已有的 `root_cause.py` 归因引擎 —— **这是别的项目做不出来的**
4. **把优化折算成钱**：絮凝剂单耗对比 + 年化节约，让"AI 优化"有财务口径
5. **反直觉结论的可视化**："排放速率开到最大反而次优"这件事，本身就是很好的演示点
6. **物理机理驱动的仿真自洽**（见第六章）：数据不是随机数，受物料平衡与沉降关系约束

## 六、数据方案（★ 老板最关心的真实性）

无真实在线仪表，采用**物理机理驱动的工况仿真**，且必须满足以下**跨模块一致性约束**：

### 6.1 内部物理自洽（硬约束）

| 关系 | 约束形式 |
|---|---|
| 物料平衡 | 给料固体通量 = 底流固体通量 + 溢流固体通量（**残差可检验**）|
| 沉降动力学 | 底流浓度 ↑ ← 泥床高度 ↑、停留时间 ↑、絮凝剂单耗 ↑ |
| 扭矩耦合 | 耙架扭矩 ↑ ← 泥床高度 ↑（超限即"压耙"）|
| 跑浑机理 | 溢流浊度 ↑ ← 絮凝剂不足 / 给料量突增 / 泥床过高 |
| 因果方向 | 超前量不能反向决定滞后量（延续 root_cause 的 `_decay` 原则）|

### 6.2 跨模块一致性（★ 关键）

- **溢流浊度** 必须与 `water_readings` 中 W3（尾矿浓密机溢流）**同源同值**，绝不能两套数打架
- **给料量** 跟随 flotation 记录的尾矿产出节奏（浮选处理量越大，进浓密机的尾矿越多）
- **底流浓度偏低 → 溢流 SS 上升 → 回水评分下降**，这条链在三个模块里方向必须一致

### 6.3 工况脚本（演示用，可复现）

| 脚本 | 表现 | 演示价值 |
|---|---|---|
| 正常稳态 | 底流 68~72%，泥床 5~6m | 基线 |
| 絮凝剂不足 | 单耗降到 25 g/t → 溢流浊度 5min 内 40→320 NTU（跑浑） | 与 water 的 W3 跑浑事件**同一起** |
| 泥床上涨 | 排放速率偏低 → 泥床 6→8m，扭矩 55→85%（压耙预警） | 前瞻预测演示 |
| 给料突增 | 上游波动 → 停留时间不足 → 底流浓度跌到 58% | 前馈推荐演示 |
| 过度排放 | 排放速率拉满 → 底流浓度不升反降 + 絮凝剂浪费 | ★ 验证"最大化排放次优" |

## 九、风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| **与 water 模块重复** | 都涉及尾矿浓密机、都涉及时序 | 边界：water 管**水**、tailings 管**设备与固体**；溢流量**同源同值** |
| **与 safety 模块角色重叠** | 尾矿库安全监测也属"安全" | 若做，定位为"设备/构筑物安全"而非"人员安全"，或干脆不做（待决策）|
| **数据真实性追问** | 无真实仪表 | 物理关系式来自文献；提供**物料平衡残差**作为自洽性证据；固定 seed 可复现 |
| **仿真会不会像编的** | 老板对"数据假"零容忍 | 全部阈值与关系附文献出处；跨模块数字强制同源；不做"完美相关"（water 经验：r 从 -0.97 调到 -0.69）|
| **无开源可抄** | 调研证实空白 | 技术骨架用平台已验证的 XGBoost + 规则引擎，**不引入重型时序框架** |
| **P80/粒度数据可用性** | 给料粒度影响沉降，但 grinding 只有 27 条 | 粒度作为**软测量输入的可选特征**，缺失时降级为不含粒度 |

## 十、★ 已确认决策（2026-10-14）
